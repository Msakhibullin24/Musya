# Фундамент проекта

Прочитай этот файл при первом подключении к проекту, при незавершённом
фундаменте или изменениях стека, границ модулей, данных и команд проверки.
Работай в реальном корне репозитория; в монорепозитории учитывай все пакеты.

## Обследование и исходное состояние

Прочитай проектные инструкции, манифесты, lock-файлы, точки входа,
публичные интерфейсы, схему данных, тесты и CI. Найди реальные команды
установки, запуска, сборки и проверки. Не запускай скрипт, не поняв его
побочные эффекты. Зафиксируй исходные результаты проверок до изменений.
Найди незакоммиченные изменения и сохраняй их при дальнейшей работе.

Для нового проекта сначала установи пользовательский сценарий, входы,
выходы и ограничения. Если стек не задан, выбери самый простой подходящий
и кратко обоснуй его. Не выбирай облако, сервисы и платные зависимости
без необходимости. Начни с минимального работающего сквозного сценария.

Для существующего проекта обследуй и исправь фундамент всего проекта,
включая участки вне текущей фичи. Это режим по умолчанию, выбранный
пользователем. Сохраняй поведение, совместимость и выбранный стек;
перестройка фундамента сама по себе не требует замены фреймворка или
распределённой архитектуры. Нехватка продуктовых требований не даёт
основания придумывать новые функции.

## Что обеспечить

| Область | Проверяемый результат |
| --- | --- |
| Запуск | Из чистого окружения доступны установка, запуск и сборка; версии и зависимости воспроизводимы средствами стека. |
| Архитектура | Названы ответственность модулей, разрешённые зависимости, публичные интерфейсы и границы доверия. Существенные запреты закреплены API, типами, линтером или тестом границ. |
| Данные | Внешний ввод валидируется на входе; ошибки не теряют данные; изменения хранения имеют безопасную миграцию и проверенный путь восстановления. |
| Качество | Есть форматирование, статические проверки по возможностям стека, тесты поведения и регрессий. Правила реально подключены к команде проверки. |
| Сквозной сценарий | CLI-драйвер запускает реальное поведение приложения в тестовом окружении и возвращает ненулевой код при ошибке. |
| Автоматизация | Одна штатная команда запускает обязательные проверки; настроенный CI использует ту же команду. |
| Контекст | Документация отражает текущее устройство, контракты, инварианты, команды и результаты проверок. |

Проверяй применимость по фактам: библиотека без хранилища не требует
БД и миграций, проект без UI не требует браузерных тестов. Отметь причину
неприменимости; это не разрешает пропустить CLI-драйвер, Feature Map,
инварианты и артефакты проверки. Для библиотеки драйвером может быть
проверочный вызов публичного API; для набора навыков — проверка пакета
и прогоны реалистичных задач в изолированных проектах.

Не создавай пустые слои и обёртки. Запрет должен соответствовать реальному
риску, например обходу валидации, доступу к хранилищу из UI или импорту
внутреннего API. Если язык не позволяет выразить нужное ограничение
типами, используй следующий доступный уровень исходной пирамиды.
Проверь, что заведомо запрещённый пример действительно отклоняется.

Используй существующий task runner и CI-провайдер. Если команды общей
проверки нет, добавь её средствами проекта; не строй универсальный
оркестратор. Если CI отсутствует, определи провайдера из проекта и
настрой его. При неизвестном провайдере подготовь локальную команду,
запроси только недостающее решение и явно оставь CI незавершённым.
Создание конфигурации не означает публикацию и включение внешнего сервиса.

## Документы и доказательства

Найди существующие документы с нужным назначением и обновляй их на месте.
Не создавай параллельный набор описаний. Если эквивалентов нет, используй:

- `AGENTS.md`: короткая инструкция для агента — точки входа, команды,
  ограничения, имя навыка `anti-slop` и документы проекта. Путь к навыку
  агент находит в своём списке доступных навыков; не записывай личные
  абсолютные пути в общие инструкции проекта. Сохраняй чужие инструкции;
  добавляй только сведения, подтверждённые проектом.
- `docs/engineering/FOUNDATION.md`: стек, модули и зависимости, контракты,
  границы доверия, инварианты с механизмами защиты, исходные сбои,
  реальные команды и оставшиеся препятствия.
- `docs/engineering/FEATURE_MAP.md`: таблица «поведение → точка входа
  в коде → инвариант → позитивная и негативная проверки → команда →
  артефакт результата». Покрой существующие функции проекта, а не только
  последнюю правку; неизвестное пометь как непроверенное.
- `.anti-slop/runs/`: журналы запусков и отчёты ревью. Добавь каталог
  артефактов в существующий ignore-файл, сохранив его содержимое.
  Не записывай секреты и персональные данные в отчёты.

Не заполняй документы догадками. Ссылки на код, символы и команды должны
существовать; статус теста подтверждается запуском, а не наличием файла.
Построение фундамента не включает установку самого навыка: не создавай
в каждом проекте его копию или ссылку в `.agents/skills/`. Постоянное
подключение настраивается один раз по [activation.md](activation.md).

## Готовность и повторное применение

Исправляй обнаруженные проблемы последовательно, проверяя сохранение
поведения. Для изменения публичного контракта или схемы сначала прочитай
[design-review.md](design-review.md). Все обязательные области должны
иметь рабочую проверку либо конкретное препятствие. Сам список задач
не считается построенным фундаментом.

После исправлений пройди [verification.md](verification.md) и независимое
ревью по [design-review.md](design-review.md). Зафиксируй, что проверено
и на каком состоянии исходников; при грязном дереве одного commit SHA
недостаточно — сохрани список изменений и хеши затронутых файлов.

При следующем запросе перечитай состояние проекта и проверь актуальность
этих сведений. Запись «готово» не заменяет проверку. Если фундамент уже
работает, используй его без повторного создания файлов, перестройки
архитектуры и дублирования конфигурации. Повторное подключение должно
быть идемпотентным, кроме новых результатов запусков.
